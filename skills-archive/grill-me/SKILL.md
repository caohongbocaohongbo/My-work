# Grill Me — 需求拷问

对需求进行系统性追问，暴露盲点、矛盾与遗漏，帮助完善需求质量。跨智能体通用，可在任意 Agent 中调用。

## Goal

通过结构化的「拷问」流程，把模糊、不完整或存在矛盾的需求拆开逼问，最终产出一份有清晰边界、可执行的需求结论或待确认问题清单。

## Inputs

触发后立即进入拷问模式，不需要预先给定参数。当前上下文中已有的需求描述、设计文档或对话内容即为拷问对象。

## Steps

### 1. 摸清当前需求现状

读取上下文中已有的需求信息（对话、文档、代码注释均算）。若有明确文件，读取相关文档。整理出：

- 已知是什么（What）
- 已知为什么（Why）
- 已知给谁用（Who）
- 已知怎么做（How）
- 明显缺失的部分

**Success criteria**：已建立需求现状的初始快照，能列出已知与未知。

### 2. 五维拷问

围绕以下五个维度逐一追问，每个维度提 2-4 个问题，不放过模糊表述：

**① 目标与价值**
- 这个需求解决的核心痛点是什么？用户现在怎么解决这个问题？
- 如果不做这个需求，会发生什么？损失有多大？
- 成功的衡量标准是什么？有可量化的指标吗？

**② 边界与范围**
- 这个需求明确不包含什么？
- 边缘场景怎么处理（空数据、网络断开、并发、权限不足）？
- 和哪些已有功能/系统有交集，交集部分谁负责？

**③ 用户与场景**
- 具体是谁在什么场景下触发这个需求？
- 用户的技术背景和操作习惯是什么？
- 有没有需要区别对待的用户分层（权限、角色、频率）？

**④ 约束与依赖**
- 有哪些硬性技术约束（性能、兼容性、安全、法规）？
- 依赖哪些外部系统或团队？他们的时间线对齐了吗？
- 数据从哪来，谁维护，格式是什么？

**⑤ 风险与反例**
- 这个需求最可能在哪里失败？
- 有没有会被这个需求影响到但没被提到的用户或流程？
- 如果某个假设被证伪，整个需求方向会怎么变？

**Success criteria**：每个维度都有实质性的问题被提出，没有因为「显然」而跳过的维度。

### 3. 挖矛盾与隐含假设

检查需求描述中是否存在：

- 互相矛盾的表述（如「要快」但「要全」、「简单」但「灵活」）
- 隐含但未说出口的假设（如「用户会主动刷新」、「数据量不超过 1000 条」）
- 被当作已知但实际未确认的前提

对每个矛盾或假设，明确指出并要求确认。

**Success criteria**：至少找出 1 个矛盾或隐含假设；若真的没有，说明为什么。

### 4. 输出拷问结论

汇总成以下结构：

```
## 需求拷问结论

### 已明确
（列出本次拷问后确认清楚的内容）

### 待确认（阻塞项）
（列出必须回答才能继续的问题，加优先级标记）

### 建议补充
（列出不影响启动但建议补充的细节）

### 发现的矛盾/假设
（列出需要对齐的矛盾点或需要验证的隐含假设）
```

如果用户回答了拷问问题，把答案并入需求文档或当前上下文，然后判断是否还有新的问题浮现。

**Success criteria**：产出结构化结论；待确认项有清晰的问题描述，不是模糊的「需要更多信息」。

## Rules

- 拷问时不预设答案，只提问题；不要假装知道用户的意图。
- 对模糊词（「尽快」、「简单」、「大概」、「差不多」）必须追问具体数字或标准。
- 不要因为问题「显而易见」就跳过——显而易见的问题最容易藏雷。
- 拷问完成后，如果用户要求，可以直接帮助修改需求文档，把拷问结论写入。
- 跨智能体通用：可在前端、UX、产品、工程等任意 Agent 上下文中调用，拷问对象随 Agent 场景自适应。
